# Change request 0025: the exact shape of the two agent wrapper procedures

- Requested by: Brave, 2026-11-07. Follows change request 0023, accepted by Sigma with the wrapper in the `agt` schema.
- Needed by module / phase: Biometric, Phase 8 step 0502 (`Revolution.Agent`).
- What is missing or wrong in the shared code: Sigma's reply fixes the procedure names but not the parameter types or the result columns. `Revolution.Agent` is written against the shape below, so Sigma's procedures must match it or this request must be changed.
- Proposed signature or schema change:
  1. `agt.usp_Agent_Devices(@AgentKey NVARCHAR(100))` returns one row per active device of the key's company with exactly these columns: `DeviceCode NVARCHAR(30)`, `Brand NVARCHAR(30)`, `Host NVARCHAR(100)`, `Port INT`, `LastPunchTime DATETIME2(0) NULL`.
  2. `agt.usp_Agent_Ingest(@AgentKey NVARCHAR(100), @DeviceCode NVARCHAR(30), @PunchesJson NVARCHAR(MAX))` returns one row with `Received INT`, `Inserted INT`, `Unmatched INT` (the three columns `att.usp_Punch_Ingest` already returns). The JSON is the array `att.usp_Punch_Ingest` reads.
  3. The agent key is sent as text: the base64 of the 32 random bytes. The wrapper hashes it and compares in constant time as Sigma described. If Sigma wants `VARBINARY(32)` instead, say so and Brave changes one line in `SqlAgentGateway`.
  4. Any failure (unknown key, retired key, unknown device code, a device code of another company) may raise one error with any number; the agent turns every `SqlException` into the same message and logs only that.
- Workaround until done: `RevolutionAgent once` fails with "The server did not accept the request." until the procedures exist.
- Sigma's decision (accepted / changed / rejected) and date: **Accepted exactly as proposed, 2026-11-08.** Sigma's procedures in 0031 will match this shape, and the types agree with `att.Device` (DeviceCode NVARCHAR(30), Brand NVARCHAR(30), Host NVARCHAR(100), Port INT).

1. **`agt.usp_Agent_Devices(@AgentKey NVARCHAR(100))`**: one row per active device of the key's company, columns `DeviceCode`, `Brand`, `Host`, `Port`, `LastPunchTime DATETIME2(0) NULL` (newest stored punch time of that device, NULL if none), in that order and with those names.
2. **`agt.usp_Agent_Ingest(@AgentKey NVARCHAR(100), @DeviceCode NVARCHAR(30), @PunchesJson NVARCHAR(MAX))`**: one row `Received`, `Inserted`, `Unmatched`, taken from `att.usp_Punch_Ingest` and passed through unchanged. The JSON is the array that procedure reads (Brave's `PunchesJson` is already written to it).
3. **Key as text: keep `NVARCHAR(100)`, no change to `SqlAgentGateway`.** The wrapper decodes the base64 (44 characters for 32 bytes), takes SHA-256 of the 32 bytes and finds the registration by that hash. A correction to my reply on 0023: I wrote "compared in constant time"; T-SQL gives no such comparison, and none is needed here, because the lookup is by the hash of a 256-bit random key, which leaks nothing useful by timing. A key that is not valid base64 or not 32 bytes is treated as unknown.
4. **One error for every failure: 53400** (message "The agent request was refused.") for unknown, retired or malformed key, unknown device code and a device code of another company, with no company or device detail in it. Numbers 53400 to 53409 are reserved for `agt`; Brave's gateway ignores the number, as proposed.
5. **Not an answer to anything else:** the agent code, its settings protection and its tests are accepted as pushed; none of it needs a change for the wrapper. Brave's `IFactoryLookup` wait (device registration screen) is unchanged and comes with the same push as 0030 and 0031.
