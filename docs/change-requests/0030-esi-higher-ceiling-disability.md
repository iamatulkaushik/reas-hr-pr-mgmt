# Change request 0030: ESI higher wage ceiling for an employee with a disability

- Requested by: Aatul (owner direction, 2026-11-14). Found while checking known-answer case C06 against the code.
- Needed by module / phase: Phase 5 gate (payroll known-answer tests). Touches employees (0100-0199), statutory (0400-0499) and payroll (0300-0399) lanes. Sigma reviews every migration.
- What is missing or wrong in the shared code: ESI covers wages up to 21,000 a month, and up to **25,000 for a person with a disability** (ESIC coverage page, 2026-11-14; ceiling fixed at 25,000 from 2008, unchanged by the 2017 revision to 21,000). The code has no way to apply it: `stat.EsiRate` holds one `WageCeiling`; `EsiCalculator.Calculate(esiWage, dailyWage, rate, stayEligible)` has no flag; `mst.EmployeeStatutory` has no field for it. An employee with a disability and wages of 24,000 is treated as not eligible, so ESI is not deducted. This is a wrong result, not a missing nicety.
- Proposed signature or schema change:
  1. **Rate row (statutory lane, 0416):** `stat.EsiRate.DisabledWageCeiling DECIMAL(12,2) NULL`. NULL means "same as WageCeiling". Set 25000 on the 2019-07-01 row. That row was CA-verified in 0411 before the column existed, so `Verified` is left as it is and the 25,000 is **not** covered by that sign-off: migration 0416 adds a note to `SourceRef` and the CA must confirm it. `EsiRate` gets an optional constructor argument `disabledWageCeiling As Decimal? = Nothing` and `Function CeilingFor(higherCeiling As Boolean) As Decimal` (returns the disabled ceiling when the flag is set and the value is not NULL, otherwise `WageCeiling`). Update `SqlStatutoryRateRepository` to read the column.
  2. **Employee flag (employees lane, 0110):** `mst.EmployeeStatutory.EsiHigherCeiling BIT NOT NULL DEFAULT 0`. Name is neutral on purpose. Store a flag only: no certificate image, no disability type, no certificate number (sensitive personal data under the DPDP Act; keep what the ceiling needs and nothing more). Re-create `usp_EmployeeStatutory_Get` and `_SaveFlags` with the column. `StatutoryFlags` gets `EsiHigherCeiling As Boolean`; `EmployeeStatutoryService` and `SqlStatutoryFlagsRepository` pass it. The flag is meaningful only when `IsEsiMember` is true; the service refuses it otherwise.
  3. **Calculator:** `EsiCalculator.Calculate(..., stayEligible As Boolean, Optional higherCeiling As Boolean = False)`. Eligibility becomes `esiWage > 0 AndAlso (stayEligible OrElse esiWage <= rate.CeilingFor(higherCeiling))`. Existing callers keep compiling.
  4. **Payroll (payroll lane):** `RunEmployeeFacts` and `ArrearsMonthInput` get an optional `esiHigherCeiling As Boolean = False`, set from the employee flag by the run input proc (re-create the 0311 read proc and the arrears preparer). `PayrollRunCalculator` and `ArrearsCalculator` pass it through. Both the "due" and "paid" arrears sides use the same flag.
  5. **Screen (Sigma):** one checkbox on the Statutory tab, enabled only when ESI member is ticked. Label: "ESI higher wage ceiling applies (person with disability)". Help text names the 25,000 limit. Permission: same as other statutory flags. Not shown in lists or on payslips.
- Tests to add (known answers, values from `known_answer_cases_2026-27.xlsx` C06):
  - Flag on, ESI wage 24,000: eligible, employee 180, employer 780 (rounded up).
  - Flag on, 25,000: eligible. 25,001: not eligible. Flag off, 24,000: not eligible.
  - Flag on, stay-eligible on, 26,000: still eligible (contribution-period rule wins).
  - Rate row with NULL disabled ceiling and flag on: uses 21,000.
  - Arrears: both sides honour the flag.
- Built 2026-11-14 (not compiled, not run on SQL Server): migrations 0110, 0344, 0416; `EsiRate.CeilingFor`; `EsiCalculator`, run and arrears calculators; statutory flag in the Employees module; 7 new tests (5 calculator, 2 employee service). Screen checkbox still Sigma's. Run order: 0110, then 0344 (it reads the new column), then 0416.
- Found while building: `SqlPayrollRunRepository` passes `esiStayEligible = False` for every employee, so the contribution-period rule (stay in until the period ends) is not applied in the regular run at all; only arrears carries the flag through. Not changed here. The CA decision on the overtime and ESI ceiling question depends on it: a separate CR should say where the stay-eligible value comes from.
- Workaround until done: none that is correct. Do not mark such an employee stay-eligible: that skips the ceiling for good.
- Related, not part of this CR: the overtime and ESI ceiling question (workbook C08). The code tests the ceiling on the same wage it contributes on, and `PayPolicy.OtInEsiWage` decides whether overtime is in that wage. ESIC practice tests the ceiling without overtime and contributes with it. The CA should decide how `EsiStayEligible` and `OtInEsiWage` are to be used together; a separate CR follows if the answer needs code.
- Open for the CA: confirm 25,000 for FY 2026-27 and that no certificate detail must be held by the employer; confirm the flag drives only the ceiling and not the 0.75 / 3.25 split.
