# Change request 0023: agent key and the wrapper that stores punches

- Requested by: Brave, 2026-11-04. Phase 8 step 0501; Owner decision 2026-11-04: eSSL first.
- Needed by module / phase: Biometric, Phase 8.
- What is missing or wrong in the shared code: ADR 0012 and 0013 give the agent its own login and a key bound to one installation and one company, with Sigma's tables and procedures; they do not exist yet. Brave built the punch tables, the storing procedure `att.usp_Punch_Ingest` and the module (migrations 0500 to 0502) and needs the part in front of it.
- Proposed signature or schema change:
  1. The agent key and registration tables (Sigma's lane) and a wrapper procedure, for example `sec.usp_Agent_Ingest(@AgentKey, @DeviceCode, @PunchesJson)`, that finds the key, checks it is active, takes the company from the registration, sets the company in the session and calls `att.usp_Punch_Ingest(@CompanyID, @DeviceID, @PunchesJson)`. The device is looked up by company and `DeviceCode`, so the agent never sees a numeric id from another company.
  2. `att.usp_Punch_Ingest` is not granted to the app login or to the agent login. Only the wrapper may call it. It takes the company as a parameter on purpose, and it expects the wrapper to have set `SESSION_CONTEXT` first, because the tenant filter policy (0501) hides rows otherwise.
  3. A way for the agent to read its own device list (code, brand, host, port, newest stored punch time) through a second wrapper, such as `sec.usp_Agent_Devices(@AgentKey)`, returning only that company's active devices. Brave's `PunchPullCoordinator` needs exactly those columns.
  4. Review of migrations 0500 (tables), 0501 (tenant policy) and 0502 (procedures), error numbers 53300 to 53306.
- Workaround until done: punches cannot be stored from outside a test. Devices, cards and the punch list work for a signed-in user.
- Sigma's decision (accepted / changed / rejected) and date: **Accepted with changes, 2026-11-07.**

1. **Wrapper goes in a new schema `agt`, not `sec`.** `hrms_app` has EXECUTE on the whole of `sec` and `att` (0006), so a wrapper in `sec` could be called by any signed-in user, and the statement in this request that `att.usp_Punch_Ingest` is "not granted to the app login" is **not true today**: the schema grant covers it. Because it takes `@CompanyID` as a parameter and the tenant policy is a filter only, a signed-in user could write punches into another company. Fix, in Sigma's lane: `agt` schema, `GRANT EXECUTE ON SCHEMA::agt TO hrms_agent` only, and `DENY EXECUTE ON OBJECT::att.usp_Punch_Ingest TO hrms_app`. The wrapper reaches the procedure through ownership chaining (same owner), so `hrms_agent` needs no grant on `att`.
2. **Wrapper names.** `agt.usp_Agent_Ingest(@AgentKey, @DeviceCode, @PunchesJson)` and `agt.usp_Agent_Devices(@AgentKey)`, as proposed. Company is read from the registration row, then set with `sp_set_session_context 'CompanyID'` inside the wrapper (this settles the open row-level-security question in ADR 0012). Agent key: 32 random bytes, only the hash stored, compared in constant time; an inactive or unknown key gives one generic error and no company information.
3. **Tables (Sigma, 0030 onward).** `sec.AgentRegistration` (company, installation id, key hash, active flag, created and retired, last seen) and issue, retire and rotate procedures for Owner and Associate. The device list returns code, brand, host, port and newest stored punch time only, active devices of that company.
4. **Review of 0500 to 0502.** Approved with one change: the DENY above. Error numbers 53300 to 53306 stay as they are. `hrms_agent` is created by the Setup tool (it does not exist anywhere yet); its connection string stays machine-protected on the agent computer.
5. **Leak tests.** I add the agent cases to the tenant leak test: wrong key, retired key, key of company A with a device code of company B, and `hrms_app` calling `att.usp_Punch_Ingest` (must be denied).

Order: 0030 `agt` schema and registration tables, 0031 wrapper procedures and DENY, then tests and the Setup change. Brave can code `Revolution.Agent` against the two wrapper signatures above now.

**Built by Sigma, 2026-11-08; changed the same day by the Owner's decision that biometric is a special build (ADR 0021).** Standard migration 0505 (first written as 0030, which failed on a new database because the procedure is created by 0502; ADR 0024) (`DENY EXECUTE` on `att.usp_Punch_Ingest` for `hrms_app`, in every database). In `database/special/biometric`, applied only for a special build: 0900 (`sec.AgentRegistration`, `sec.usp_Agent_Issue`, `_List`, `_Retire`; Owner, Associate of the company or Developer only; errors 53410 to 53412) and 0901 (schema `agt`, role `hrms_agent`, `agt.usp_Agent_Authenticate` internal, `agt.usp_Agent_Devices`, `agt.usp_Agent_Ingest`; error 53400). `RevolutionSetup create-agent-login <name>` creates the SQL login in the role. 12 database tests in `AgentWrapperTests` (they need `HRMS_TEST_CONNECTION`; not run here, no SQL Server). `sec.AgentRegistration` has a company column and no filter policy on purpose (the wrapper finds the company from the key); the policy test exempts it, and it is outside `database/migrations`, so guard 6 does not see it. Still open for a special build: the screen for the Owner or Associate to issue, list and retire keys (the three procedures are ready).
